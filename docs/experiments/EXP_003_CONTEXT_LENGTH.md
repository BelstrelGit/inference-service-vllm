# EXP_003 — Context length (Exp2)

**Дата:** 2026-10-18
**Статус:** done
**Series:** `l4-qwen7b-bf16-v1` (полный прогон), `l4-qwen7b-bf16-v1-pilot` (пилот)

---

## Question

Как длина промпта (при фиксированном выходе 128 токенов) меняет prefill, TTFT, TPOT и throughput, и сдвигается ли граница насыщения по concurrency так, как предсказывает гипотеза об ограничении ёмкостью KV cache из [EXP_002](EXP_002_CONCURRENCY.md)?

Две части в одном отчёте:
- **Exp2A, prefill:** c=1, промпт 128 / 512 / 1024 / 2048 / 4096, плюс одна точка 7168 для проверки длинного контекста.
- **Exp2B, сдвиг насыщения:** промпт 1024 / 2048 / 4096, развёртка по c вокруг предсказанной границы KV.

## Environment

- Как в [EXP_002](EXP_002_CONCURRENCY.md): GKE `us-central1`, `g2-standard-8` + 1 × L4; vLLM 0.30.0, Qwen2.5-7B-Instruct bf16, `k8s/serving/vllm.yaml` (`max-model-len 8192`, `max-num-seqs 256`, `max-num-batched-tokens 2048`, chunked prefill, prefix caching).
- KV cache 53,696 tokens (лог vLLM при старте 2026-10-18, как и 2026-10-17); 56 KiB/token, то есть ~2.9 GiB.
- Client: `client.load` без изменений, серия `l4-qwen7b-bf16-v1`.

## Hypothesis

Записана до пилота. Числа ниже — ориентиры из грубых оценок, а не предсказания с допуском.

**Exp2A (c=1):**
- Серверный prefill растёт с длиной промпта. Линейность не предполагаем: при `max-num-batched-tokens 2048` промпт длиннее 2048 токенов требует chunked prefill: номинально не меньше 2 чанков для 4096 и 4 для 7168. Фактическое число итераций может быть больше, потому что в одну итерацию с prefill входят и decode-токены других запросов. Форма кривой после 2048 может отличаться от формы до 2048. Ориентир по порядку величины: prefill 4096 токенов ~1 с, 7168 ~2 с (масштабирование 155 мс при 512 токенах по объёму вычислений).
- TPOT при c=1 растёт слабо, меньше чем на 10% от 512 до 7168. Шаг decode при c=1 ограничен чтением весов (~15 GiB), а KV одной последовательности даже при 7296 токенах ~0.4 GiB.
- E2E ≈ TTFT + 127 × TPOT. Рост E2E с длиной промпта определяется в основном TTFT.

**Exp2B (сдвиг насыщения):**
- Признаки давления на KV (KV max ≈ 1, preemption > 0, `waiting` > 0) возникают при меньшей concurrency, чем длиннее промпт. Ожидаемая область границы: между 53,696 / (P + 128) (все последовательности в конце генерации) и 53,696 / (P + 64) (в среднем половина выхода):

  | Prompt P | P + 128 | граница, последовательностей | признаков нет при | признаки есть при |
  |---|---|---|---|---|
  | 512 (Exp1) | 640 | 84–93 | c ≤ 64 (наблюдалось) | c ≥ 96 (наблюдалось) |
  | 1024 | 1152 | 47–49 | c ≤ 40 | c ≥ 56; c=48 пограничный |
  | 2048 | 2176 | 25 | c ≤ 20 | c ≥ 28; c=24 пограничный |
  | 4096 | 4224 | 13 | c ≤ 10 | c ≥ 14; c=12 пограничный |

- **Учёт токенов в KV.** На насыщенных уровнях занятые токены, `KV mean × 53,696`, примерно равны `running mean × (P + 64)` (расхождение в пределах ~10%). Проверка на Exp1 при c=96: 0.94 × 53,696 ≈ 50.5k и 86.5 × 576 ≈ 49.8k. Это сравнение сильнее, чем просто «граница по c сдвинулась»: оно проверяет, что при насыщении в KV находится примерно ёмкость пула, независимо от длины промпта.
- Бюджет токенов на итерацию не ожидается основным ограничением в установившемся режиме. В равномерном потоке средняя потребность — примерно c × (P / 128 + 1) токенов на итерацию, максимум 16 × 33 = 528 при P=4096 и c=16, заметно меньше `max-num-batched-tokens` 2048. Это средняя оценка: локальные всплески и конкуренция chunked prefill она не исключает. Если `waiting` появится при невысоком KV usage и без preemption, нужно отдельно проверить конкуренцию за бюджет токенов в планировщике как альтернативный механизм.
- Максимальный `steady tok/s` ниже, чем в Exp1, и падает с ростом P: одновременно декодируется меньше последовательностей, а итерации несут больше работы prefill и attention.

**Что опровергает гипотезу о KV:** граница по c не сдвигается с P; или на насыщенных уровнях `running × (P + 64)` заметно расходится с `KV mean × 53,696`. `waiting` при невысоком KV usage и без preemption сам по себе гипотезу не опровергает, но указывает на другой механизм очереди (см. выше).

Exp2 — не чистая интервенция на KV: с длиной промпта растёт и объём prefill. Подтверждение здесь — сдвиг в предсказанном направлении и согласованный учёт токенов. Изменение ёмкости KV при том же workload — в Exp4.

## Pilot

Один прогон на уровень, окно 60 с, серия `l4-qwen7b-bf16-v1-pilot`: P=4096 на всех уровнях Exp2B и P=7168 при c=1. Цели:
- E2E при P=4096 и c=10…16: в окно 120 с полного прогона должно поместиться несколько циклов, а `stagger_s` 20 должен быть порядка E2E;

**Наблюдения без объяснения** (для проверки на полном прогоне):
- **Очередь при KV ниже 1 и без preemption** (c=14: KV mean 0.85, max 0.94). На плато `running` занятыми оказываются ~86% пула против 92–94% в Exp1 при P=512. Свободный остаток ~7.5k токенов меньше двух футпринтов последовательности по 4160, так что одна из возможных причин — более крупная гранулярность одной последовательности при длинных промптах. По секундным снимкам это не проверить; если причина в этом, при P=1024 и P=2048 доля незанятого пула на плато должна быть меньше, чем при 4096.

## Interpretation

**Exp2A: prefill пропорционален длине промпта.** От 512 до 4096 токенов серверный prefill растёт почти строго пропорционально, 0.27–0.29 мс на токен (~3600 токенов/с). При 128 токенах на токен уходит 0.55 мс: фиксированные накладные расходы итерации здесь сопоставимы с работой. При 7168 на токен уходит на ~5% больше, чем при 4096. Это согласуется с растущей долей attention в prefill, но отдельно не проверялось. Ступеньки на границе бюджета 2048 нет: prefill 4096 токенов (номинально 2 чанка) занимает 1135 мс, в 2.03 раза больше, чем 2048 (559 мс). TPOT при c=1 почти не зависит от контекста: +2.7% от 128 до 7168. E2E = TTFT + 127 × TPOT с точностью до 0.1%, то есть рост E2E с длиной промпта определяется TTFT.

**Exp2B: граница сдвигается так, как предсказывает гипотеза о ёмкости KV.**
- На всех трёх длинах промпта уровни, где признаков давления на KV быть не должно (1024: c ≤ 40; 2048: c ≤ 20; 4096: c ≤ 10), прошли без очереди и без preemption. На уровнях, где они ожидались (1024: c ≥ 56; 2048: c ≥ 28; 4096: c ≥ 14), появилась очередь. На пограничных уровнях (48, 24, 12) KV max дошёл до 0.93–0.98, но очереди ещё не было.
- `running` на плато — 90–95% верхней оценки 53,696 / (P + 64): 86, 47, 24 и 11.6 последовательности при P = 512, 1024, 2048 и 4096. Число одновременно выполняемых запросов падает почти обратно пропорционально размеру запроса в KV.
- На плато в KV при всех P находится примерно один и тот же объём, 47–51k токенов из 53,696. Это главный результат: при 8-кратном изменении длины запроса насыщение наступает при одном и том же суммарном числе токенов в KV.
- **Учёт токенов сходится.** При P ≤ 2048 KV-токенов на выполняемую последовательность на 7–8 больше, чем P + 64 (1096 против 1088, 2118 против 2112, 583 против 576 в Exp1). Это согласуется со средней потерей на округление до блока (полблока из 16 токенов). При P=4096 их на 1–2% меньше, чем P + 64. Одна из возможных причин: пока длинный промпт проходит chunked prefill, последовательность держит в KV только его часть. Не проверялось.

Это второй шаг лестницы из EXP_002: граница насыщения сдвигается вместе с потребностью запроса в KV в направлении и масштабе, которые предсказывает гипотеза. Интервенцией на ёмкость KV это не является: вместе с P растёт и работа prefill.

**Пропускная способность на плато обратно пропорциональна размеру запроса в KV.** `max steady tok/s × (P + 64)` держится в пределах 279–288k (±2%) для всех P: каждое удвоение промпта примерно вдвое снижает максимальный throughput. Это то же самое, что throughput ≈ `running на плато / TPOT на плато`, где TPOT на плато 165–180 мс при всех P (192 мс в Exp1 при c=96).

**При длинных промптах TPOT растёт с c быстрее.** При c=8 TPOT 66.7 / 90.5 / 124.2 мс для P = 512 / 2048 / 4096, при c=16 — 77.0 / 93.7 / 129.2 мс для P = 512 / 1024 / 2048. Косвенная оценка, не измерение: если считать, что токен prefill в смешанной итерации стоит столько же, сколько при c=1 (0.278 мс), то prefill занимает долю времени GPU, равную `steady tok/s / 128 × P × 0.278 мс`. Тогда «остаток» `TPOT × (1 − доля prefill)` при c ≥ 8 лежит в узкой полосе 57–76 мс для всех P и плавно растёт с `running`. Значит, разница в TPOT между длинами промптов по порядку величины объясняется временем, которое уходит на prefill чужих запросов. На плато эта доля около 0.52–0.61 при всех P: сервер обрабатывает ~1.9–2.2k токенов prefill в секунду независимо от длины промпта. Оценка не учитывает перекрытие prefill и decode в одной итерации и при c=1 неприменима: там TPOT вообще не содержит чужого prefill. Проверка — профиль итераций.

**Очередь появляется раньше, чем KV доходит до 1.** Первый признак насыщения при всех P — `waiting` без preemption: P=2048 при c=28 (KV mean 0.96) и P=4096 при c=14 (KV mean 0.88). Preemption появляется при следующем уровне c. Незанятый остаток пула на плато: ~11% при P=4096 против 4–8% при P=1024 и 2048. Это выполняет предсказание из пилота, записанное до полного прогона. В абсолютных числах остаток — 1–2.5 футпринта последовательности при P ≥ 1024, но 6–7 при P=512 (Exp1). Значит, гранулярность одной последовательности может объяснять долю остатка при длинных промптах, но не при коротких. Какое именно условие свободного места проверяет планировщик vLLM при приёме нового запроса, по метрикам не видно; механизм не утверждаем.

## Limitations

- Все запросы одной длины; смесь длин заполняет KV иначе.
- Длинные промпты из случайных токенов: стоимость attention та же, что у реального текста, но prefix cache не задействован совсем.
- Exp2 не интервенция на ёмкость KV: вместе с P растёт работа prefill на запрос. Причинное подтверждение — в Exp4.
- Доля времени GPU на prefill — косвенная оценка из стоимости prefill при c=1, а не измерение по итерациям.
- «KV-токены на running» — отношение средних по разным снимкам. При c=1 в паузах между запросами оба падают, и оценка занижена на 2–6% (P=7168: 6928 против 7232).
- Серверные метрики снимаются раз в секунду: кратковременные пики KV и очереди между снимками не видны.
- Одна сессия кластера, одна нода, одна версия vLLM. Пилот (P=4096) и полный прогон согласуются в пределах 3% по `steady tok/s` и TPOT.

## Next question

- **Exp3, длина выхода:** при фиксированном P запрос держит KV тем дольше, чем длиннее выход. Если гипотеза верна, граница должна определяться средним футпринтом P + O/2, а не P + O.
- **Exp4, причинная проверка ёмкости KV:** тот же workload, но меняется ёмкость пула через `gpu-memory-utilization` или FP8 KV. Удобнее всего при P=2048: граница предсказывается узко (~25), сетка маленькая и дешёвая.
- **Условие приёма нового запроса в планировщике vLLM 0.30:** почему очередь появляется при KV 0.88–0.96. Это можно проверить по исходному коду, без GPU.
- **Профиль итераций одной серией:** ответил бы на три вопроса — доля prefill в TPOT (Exp2), ступенька TTFT c=1 → c=2 и TPOT при c=96 против c=128 (EXP_002).
