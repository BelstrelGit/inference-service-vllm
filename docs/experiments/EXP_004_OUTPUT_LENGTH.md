# EXP_004 — Output length (Exp3)

**Дата:** 2026-10-18 (черновик дизайна)
**Статус:** draft
**Series:** `l4-qwen7b-bf16-v1`

---

## Question

Как длина выхода O при фиксированном промпте P=512 меняет TPOT, E2E и throughput, и где наступает насыщение в двух крайних режимах: prefill-heavy (O=32) и decode-heavy (O=512)?

Три части в одном отчёте:
- **Exp3A, c=1:** O = 32, 512, 1024; точка O=128 берётся из Exp1.
- **Exp3B, decode-heavy:** O=512, развёртка по c вокруг предсказанной границы KV.
- **Exp3C, prefill-heavy:** O=32, развёртка по c. Здесь ожидается насыщение не по KV, а по вычислениям prefill. Это проверка альтернативного механизма, который в Exp2 был только оговоркой.

## Environment

Как в [EXP_003](EXP_003_CONTEXT_LENGTH.md): GKE `us-central1`, 1 × L4, vLLM 0.30.0, Qwen2.5-7B-Instruct bf16, `k8s/serving/vllm.yaml` без изменений, KV cache 53,696 tokens. Client без изменений, серия `l4-qwen7b-bf16-v1`.

## Hypothesis

Черновик, до пилота. Опирается на результаты Exp1 и Exp2 и на правило приёма запросов vLLM 0.30 (EXP_003, Interpretation): новый запрос принимается, если в свободных блоках помещается его промпт; рост KV во время decode не резервируется.

**Exp3A (c=1):**
- TTFT не зависит от O (~170 мс, промпт тот же).
- TPOT растёт меньше чем на 3% от O=32 до O=1024: контекст к концу генерации растёт до 1536 токенов, а в Exp2A TPOT при c=1 вырос на 2.7% до 7296 токенов.
- E2E ≈ TTFT + (O − 1) × TPOT, то есть растёт линейно по O.

**Exp3B (O=512, decode-heavy):**
- Средний объём запроса в KV — P + O/2 = 768 токенов, верхняя оценка числа одновременно выполняемых запросов 53,696 / 768 ≈ 70. По аналогии с Exp2, где плато было на 90–95% такой оценки, ожидается `running` на плато ~63–66. Признаков давления на KV нет при c ≤ 56, есть при c ≥ 72, уровень c=64 пограничный.
- KV-токенов на выполняемую последовательность ≈ P + O/2 + 8 ≈ 776 на всех уровнях без насыщения.
- **Preemption наступает не позже, чем очередь.** Порог приёма — 512 свободных токенов (1% пула), а каждый принятый запрос потом вырастет ещё на 512 токенов. Поэтому планировщик принимает больше, чем потом поместится, и вытеснение начнётся раньше или одновременно с очередью. В Exp2 при P ≥ 2048 порядок был обратный: сначала очередь, потом preemption.
- **Throughput, количественная проверка косвенной модели из Exp2.** Если TPOT ≈ «остаток без prefill» / (1 − доля prefill), то при O=512 доля prefill в 4 раза меньше, чем при O=128 при том же output tok/s (на один выходной токен приходится 1 токен промпта, а не 4). Отсюда ожидается TPOT на плато ~90–110 мс вместо 165–190 и максимальный `steady tok/s` ~550–700. Если TPOT на плато окажется ~170 мс, как в Exp1 и Exp2, модель неверна: TPOT на плато тогда определяется не prefill, а чем-то другим (например, объёмом KV).

**Exp3C (O=32, prefill-heavy):**
- Предел по вычислениям prefill. При 0.278 мс на токен prefill (Exp2A) GPU может обработать не больше ~7 запросов с P=512 в секунду, то есть не больше ~225 выходных токенов в секунду при O=32, даже если бы вообще не тратил время на decode.
- Насыщение по `steady tok/s` наступает там, где c / E2E подходит к ~7 req/s, при KV usage заметно ниже 1 и без preemption. Очередь при этом растёт.
- Это первый эксперимент, где ожидается очередь, не связанная с KV. Она отличается от KV-насыщения по KV usage и preemption, а `waiting_by_reason` её не различает (в обоих случаях `capacity`).

**Что опровергает:** в 3B граница по c заметно (больше чем на ~15%) расходится с ~63–66; в 3C на насыщении KV usage близок к 1 или есть preemption.

## Pilot

Один прогон на уровень, короткое окно, серия `l4-qwen7b-bf16-v1-pilot`. Цели:
- E2E при O=512 на c=64…80: проверить, что окно 240 с вмещает не меньше 3 циклов, а `stagger_s` того же порядка, что E2E;
- грубое положение границы при O=512 и точка выхода на плато при O=32;
- нет ли таймаутов при длинных E2E и очереди (`timeout_s` 600).

## Setup

- Load mode: closed loop
- Prompt: 512 токенов, `token_ids`, уникальные промпты на прогон
- Output: 32 / 512 / 1024 токенов, `ignore_eos`, `temperature 0`
- Repetitions: 3
- Уровни и окна:

  | Сценарий | O | c | окно | warm-up | `stagger_s` |
  |---|---|---|---|---|---|
  | `exp3_out32` | 32 | 1, 8, 16, 32, 64, 96, 128 | 120 с | 10 запросов, 30 с | 10 |
  | `exp3_out512` | 512 | 1, 32, 48, 56, 64, 72, 80 | 240 с | 3 запроса, 90 с | 80 |
  | `exp3_out1024_c1` | 1024 | 1 | 240 с | 2 запроса, 30 с | 0 |

  Для O=512 E2E на плато ожидается ~60–80 с (512 × ~0.1–0.15 с), поэтому окно и разнос стартов больше, чем в Exp1. Для O=32 E2E 2–5 с, `stagger_s` 10 с перекрывает несколько циклов.
- Время GPU: O=32 ~1 ч, O=512 ~2.5 ч (7 уровней × 3 × ~7 мин), O=1024 при c=1 ~20 мин; плюс пилот ~30 мин. Итого около 4 ч.
- Вариант дешевле: в `exp3_out512` оставить c = 1, 48, 64, 72, 80 (~1.8 ч).

## Limitations

- `ignore_eos`: все ответы ровно O токенов. При реальном распределении длин выхода KV освобождается неравномерно.
- Exp3C проверяет предел prefill только при P=512. При коротких промптах накладные расходы итерации больше (0.55 мс на токен при P=128 против 0.28 при 512).
