# EXP_004 — Output length (Exp3)

**Дата:** 2026-10-20 (дизайн 2026-10-18, пилот 2026-10-19)
**Статус:** done
**Series:** `l4-qwen7b-bf16-v1` (полный прогон), `l4-qwen7b-bf16-v1-pilot` (пилот)

---

## Question

Как длина выхода O при фиксированном промпте P=512 меняет TPOT, E2E и throughput, и где наступает насыщение в двух крайних режимах: prefill-heavy (O=32) и decode-heavy (O=512)?

Три части в одном отчёте:
- **Exp3A, c=1:** O = 32, 512, 1024; точка O=128 берётся из Exp1.
- **Exp3B, decode-heavy:** O=512, развёртка по c вокруг предсказанной границы KV.
- **Exp3C, prefill-heavy:** O=32, развёртка по c. Здесь ожидается насыщение не по KV, а по вычислениям prefill. Это проверка альтернативного механизма, который в Exp2 был только оговоркой.

## Environment

Как в [EXP_003](EXP_003_CONTEXT_LENGTH.md): GKE `us-central1`, 1 × L4, vLLM 0.30.0, Qwen2.5-7B-Instruct bf16, `k8s/serving/vllm.yaml` без изменений, KV cache 53,696 tokens. Client без изменений, серия `l4-qwen7b-bf16-v1`.

## Hypothesis

Записана до пилота и до полного прогона. Опирается на результаты Exp1 и Exp2 и на правило приёма запросов vLLM 0.30 (EXP_003, Interpretation): новый запрос принимается, если в свободных блоках помещается его промпт; рост KV во время decode не резервируется.

**Exp3A (c=1):**
- TTFT не зависит от O (~170 мс, промпт тот же).
- TPOT растёт меньше чем на 3% от O=32 до O=1024: контекст к концу генерации растёт до 1536 токенов, а в Exp2A TPOT при c=1 вырос на 2.7% до 7296 токенов.
- E2E ≈ TTFT + (O − 1) × TPOT, то есть растёт линейно по O.

**Exp3B (O=512, decode-heavy):**
- Средний объём запроса в KV — P + O/2 = 768 токенов, верхняя оценка числа одновременно выполняемых запросов 53,696 / 768 ≈ 70. По аналогии с Exp2, где плато было на 90–95% такой оценки, ожидается `running` на плато ~63–66. Признаков давления на KV нет при c ≤ 56, есть при c ≥ 72, уровень c=64 пограничный.
- KV-токенов на выполняемую последовательность ≈ P + O/2 + 8 ≈ 776 на всех уровнях без насыщения.
- **Preemption вместе с очередью и чаще, чем в Exp1.** Это предсказание из правила приёма, а не наблюдение. Завершённый запрос освобождает P + O = 1024 токена, этого хватает на два новых промпта по 512. Если в очереди не меньше двух запросов, планировщик примет оба, и для роста уже выполняемых последовательностей (по токену на шаг) места не останется. Следующий блок для decode придётся брать через вытеснение. Поэтому ожидается, что при дальнейшем росте c после появления очереди preemption станут регулярными, а вытеснений на 100 запросов будет заметно больше, чем в Exp1 (10–11 при c=96 и 16–18 при c=128: 42–47 на ~434 и 72–78 на 433–440 запросов). Сравнение идёт на 100 запросов, потому что прогоны Exp1 и Exp3B различаются по длительности окна и по числу завершённых запросов, и счётчик на прогон между ними несопоставим. Знаменатель — запросы, отправленные в окне замера, а счётчик preemption берётся по серверному окну, поэтому оценка приблизительная. Вытесненный запрос заново проходит prefill, так что за границей `steady tok/s` может не только выйти на плато, но и снизиться. В Exp2 при P ≥ 2048 освобождённого места (P + 128) хватало ровно на один новый промпт и 128 токенов роста, и очередь появлялась раньше preemption (P=2048: c=28 без preemption, при c=32 их 6; P=4096: c=14 без preemption, при c=16 их 6). Оговорка: при P=512 и O=128 баланс такой же (640 = 512 + 128), но в Exp1 preemption появилась вместе с очередью. Значит, арифметика одного освобождения объясняет не всё, и проверяется здесь в первую очередь число вытеснений на 100 запросов.
- **Throughput, количественная проверка косвенной модели из Exp2.** Если TPOT ≈ «остаток без prefill» / (1 − доля prefill), то TPOT ≈ d(n) + n × 142 мс / O, где 142 мс — prefill одного промпта P=512 (0.278 мс × 512), а d(n) — остаток TPOT без prefill. По Exp1 при c=64 d ≈ 144 − 64 × 142 / 128 ≈ 73 мс; при среднем контексте 768 вместо 576 он немного больше. При O=512 добавка prefill равна 64 × 142 / 512 ≈ 18 мс. Отсюда ожидается TPOT на плато ~90–110 мс вместо 165–190 и максимальный `steady tok/s` ~550–700. Это экстраполяция d(n) из Exp1, а не измерение. Если TPOT на плато окажется ~170 мс, как в Exp1 и Exp2, модель неверна: TPOT на плато тогда определяется не prefill, а чем-то другим (например, объёмом KV). Результат 120–150 мс не решает вопрос в пользу ни одного варианта: модель могла верно уловить направление, но ошибиться в d(n).

**Exp3C (O=32, prefill-heavy):**
- Ориентир по стоимости prefill одного запроса, а не физический потолок. При c=1 prefill P=512 стоит ~142 мс (0.278 мс на токен, Exp2A). Если стоимость prefill на запрос не уменьшается при батчинге, GPU обработает ~7 запросов в секунду, или ~225 выходных токенов в секунду при O=32, даже если на decode время не тратится совсем. Батчинг может сделать prefill дешевле, и тогда значение выше 7 req/s не противоречит механизму: оно значит лишь, что стоимость при c=1 завышает стоимость в батче.
- Косвенная оценка с учётом decode по той же формуле, что для 3B: TPOT ≈ d(n) + n × 142 мс / 32. На один выходной токен приходится в 4 раза больше prefill, чем при O=128, поэтому TPOT растёт с c гораздо быстрее, чем в Exp1:

  | c | TPOT, мс | req/s | output tok/s |
  |---|---|---|---|
  | 8 | ~95 | ~2.7 | ~85 |
  | 16 | ~130 | ~3.9 | ~125 |
  | 32 | ~210 | ~4.8 | ~155 |
  | 64 | ~360 | ~5.6 | ~180 |

  d(n) взят из Exp1, где TPOT = d(n) + n × 1.1 мс. Таблица — экстраполяция по косвенной модели, а не измерение; проверяется прежде всего форма кривой, а не точные значения.
- Насыщение плавное, без излома: в этой модели req/s подходит к ~6, а не к ориентиру 7, потому что decode занимает время GPU и при больших c. От KV-насыщения оно отличается тем, что `running` ≈ c, KV usage не выше ~0.85, preemption нет, а серверный queue time порядка одной итерации. E2E растёт за счёт TPOT, а не очереди. Бюджет итерации в 2048 токенов вмещает decode и до ~3 новых промптов, а приходит в среднем ~2 промпта за итерацию (5.6 req/s × ~0.36 с при c=64). Признаки по `waiting_by_reason` здесь не помогут: он и в этом случае показывает `capacity`.
- Граница KV для O=32: 53,696 / (512 + 16 + 8) ≈ 100, плато ожидается при ~90–95. Поэтому сетка ограничена c ≤ 80 (KV не выше ~0.8), чтобы два механизма не смешивались.

**Что опровергает:**
- 3B: плато `running` отличается от ~63–66 больше чем на ~15%; TPOT на плато ~170 мс (см. выше). Гипотеза о сильном давлении preemption при O=512 не подтверждается, если после появления устойчивой очереди preemption при дальнейшем росте c остаются редкими или их нет совсем. Одна первая перегруженная точка с очередью и без preemption сама по себе её не опровергает: в Exp2 так было при P=2048, c=28 и при P=4096, c=14.
- 3C: при c ≤ 80 KV usage близок к 1 или есть preemption. Или `steady tok/s` растёт почти линейно до c=64: тогда prefill в батче дешевле 0.278 мс на токен, измеренных при c=1. Или при c ≤ 80 queue time больше ~2 итераций: тогда ограничивает бюджет токенов на итерацию, а не время GPU.

## Interpretation

**Exp3A: при c=1 длина выхода меняет только число шагов decode.** TPOT от O=32 до O=1024 вырос на 0.2% (56.60 → 56.73 мс), меньше предсказанных 3%. E2E совпадает с TTFT + (O − 1) × TPOT с точностью до 0.01%. Клиентский TTFT p50 при этом растёт с O: 166 → 184 мс (+11%), хотя серверный prefill не растёт (153 → 145 мс). Разрыв между клиентским и серверным TTFT растёт с ~10 мс при O=32 до ~36 мс при O=1024. Предсказание «TTFT не зависит от O» выполнено по серверу, но не по клиенту. Откуда разрыв (клиент, HTTP-стек, API-сервер vLLM после длинного стрима), по этим данным не видно; на выводы Exp3B и Exp3C он не влияет: это десятки миллисекунд на фоне секунд.

**Exp3B: граница стоит там, где предсказывает средний футпринт P + O/2.**
- При c ≤ 56 признаков давления на KV нет, при c=64 KV max 0.93 без очереди (пограничный уровень), при c ≥ 72 очередь и preemption. Плато `running` 63.4–63.6 — внутри предсказанных 63–66, 91% верхней оценки 53,696 / 768. Доля пула на плато (63.5 × 780 ≈ 49.5k, 0.92) та же, что в Exp1 и Exp2 (0.88–0.96).
- KV-токенов на running 780 против 776 (P + O/2 + 8): по среднему за жизнь запроса пул учитывается так же, как в Exp2.
- Граница при O=512 лежит на c ≈ 64–72, при O=128 на ~96. Отношение плато 86 / 63.5 = 1.35 близко к отношению футпринтов 768 / 576 = 1.33. Это третий независимый признак того, что насыщение определяется числом токенов в KV: в Exp2 футпринт менялся через промпт, здесь — через выход, а prefill на запрос одинаковый.

**Exp3B: preemption — сразу вместе с очередью и в 4–5 раз чаще, чем в Exp1.** Очередь и preemption появились на одном уровне (c=72), без промежуточной точки «очередь без вытеснений», как в Exp1 и в отличие от Exp2 при P ≥ 2048. На 100 запросов 57 и 71 вытеснение при c = 72 и 80 против 10 и 16 в Exp1 при c = 96 и 128. Это выполняет предсказание из правила приёма (освобождённых 1024 токенов хватает на два промпта по 512 и не остаётся запаса на рост decode), но правило здесь не проверено напрямую: вывод по согласованию числа и порядка признаков.

**За границей throughput при O=512 падает, а при O=128 рос.** `steady tok/s` 675 → 652 → 634 при c = 64 → 72 → 80 (−3% и −6%), при этом `running` на плато не меняется (63.5), а TPOT растёт 94 → 103 → 106 мс. В Exp1 за границей `steady tok/s` продолжал медленно расти (430 → 469 → 485). Направление согласуется с повторным prefill вытесненных запросов: каждый вытесненный при повторном приёме заново считает промпт и уже сгенерированные токены, это лишняя работа в тех же итерациях. Оценку объёма этой работы по метрикам не делаем: неизвестно, на каком шаге decode вытеснялись запросы. Проверка — профиль итераций или счётчик повторно посчитанных токенов.

**Exp3B: косвенная модель TPOT при O=512 работает.** Предсказание до прогона — TPOT на плато ~90–110 мс и `steady tok/s` ~550–700; измерено 94–106 мс и максимум 675. На `output_tpot_model.png` точки O=512 лежат на диагонали в пределах нескольких процентов. Вариант «TPOT на плато ~170 мс, как в Exp1 и Exp2, независимо от O» опровергнут: при том же P и том же объёме KV на плато TPOT вдвое ниже. Значит, TPOT ~170 мс на плато в Exp1 и Exp2 определялся не объёмом KV как таковым; модель «остаток decode + доля чужого prefill» согласуется с обоими случаями. Это по-прежнему косвенная оценка из стоимости prefill при c=1, не измерение по итерациям.

**Инвариант Exp2 не переносится на другую длину выхода.** В Exp2 `max steady tok/s × (P + 64)` держался на 279–288k для всех P. При O=512 `675 × (512 + 256)` ≈ 518k: при том же числе токенов в KV на плато пропускная способность почти вдвое выше, потому что TPOT на плато почти вдвое ниже. Это согласуется с тем, что инвариант Exp2 отражал одинаковый TPOT на плато при O=128, а не только свойство пула. Это согласуется с формой throughput ≈ `running на плато / TPOT на плато`, которую Exp4 проверяет при другой ёмкости пула.

**Exp3C: насыщение плавное, без признаков KV.** При c ≤ 80 KV не выше 0.79, preemption нет, `waiting max` 0, серверная очередь ≤ 1.4 мс. `steady req/s` растёт 2.6 → 3.9 → 5.0 → 5.8 → 6.0 и подходит к ~6.5 (1 / prefill при c=1); `steady tok/s` растёт с c сублинейно (85 → 163 → 188 → 195 при c = 8 / 32 / 64 / 80). TPOT растёт до 371 мс, E2E растёт за счёт TPOT и TTFT, а не очереди. Это прогнозированная картина насыщения по времени GPU на prefill, а не по KV.

**Exp3C: косвенная модель верно предсказывает throughput, но завышает TPOT на 11–14%.** До прогона (таблица в Hypothesis): req/s 2.7 / 3.9 / 4.8 / 5.6, измерено 2.63 / 3.89 / 4.99 / 5.78; TPOT 95 / 130 / 210 / 360 мс, измерено 84 / 117 / 184 / 317. При O=512 модель точна, при O=32 завышает TPOT. Модель не различает два объяснения: prefill в батче дешевле 0.278 мс на токен, измеренных при c=1, или d(n) из Exp1 (средний контекст 576) завышен для O=32 (средний контекст 528). Throughput сходится, несмотря на ошибку TPOT, потому что TTFT при O=32 больше, чем закладывала модель (см. ниже), и E2E на запрос в сумме близок к предсказанному. Различить объяснения может профиль итераций.

**Exp3C: TTFT растёт за счёт серверного prefill, а не очереди.** Серверный prefill (от приёма запроса планировщиком до первого токена) растёт 153 → 298 → 404 → 681 → 996 мс при c = 1 / 8 / 32 / 64 / 80, при нулевой очереди. Это 2–4 средних TPOT на всех уровнях c ≥ 4 (266 / 70.5 ≈ 3.8 при c=4, 996 / 371 ≈ 2.7 при c=80). Гипотеза, не проверенная: prefill одного запроса занимает больше одной итерации — в итерацию попадает несколько промптов сразу (~2 новых запроса на итерацию при c ≥ 64), часть из них дробится chunked prefill по бюджету 2048 токенов, и время prefill каждого равно длительности нескольких «тяжёлых» итераций. Проверка — профиль итераций.

Exp3 подтверждает механизм с третьей стороны: граница насыщения по c сдвигается вместе со средним футпринтом запроса в KV (P + O/2), а при коротком выходе насыщение наступает по времени GPU на prefill раньше, чем по KV. Интервенцией на ёмкость пула это не является; это Exp4.

## Limitations

- `ignore_eos`: все ответы ровно O токенов. При реальном распределении длин выхода KV освобождается неравномерно.
- Exp3C проверяет предел prefill только при P=512. При коротких промптах накладные расходы итерации больше (0.55 мс на токен при P=128 против 0.28 при 512).
- Доля prefill и d(n) — косвенные оценки из стоимости prefill при c=1 и из Exp1, а не измерение по итерациям. Модель при O=32 завышает TPOT на 11–14%, и источник ошибки не установлен.
- Счётчик preemption берётся по серверному окну, знаменатель — запросы клиентского окна: «на 100 запросов» — приближённая величина.
- Для O=32 граница KV (~90–100) не измерялась: сетка ограничена c ≤ 80, чтобы не смешивать механизмы.
- Серверные метрики снимаются раз в секунду; одна сессия кластера, одна нода, одна версия vLLM. Пилот (один прогон, окно 60 с при O=32) и полный прогон согласуются в пределах 10%.
