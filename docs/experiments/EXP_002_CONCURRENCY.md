# EXP_002 — Concurrency scaling (Exp1)

**Дата:** 2026-10-17
**Статус:** done
**Series:** `l4-qwen7b-bf16-v1` (полный прогон), `l4-qwen7b-bf16-v1-pilot` (пилот)

---

## Question

Как меняются output throughput, TTFT, TPOT и очередь с ростом concurrency (closed loop, 512 → 128), на каком уровне наступает насыщение и какой ресурс его определяет?

## Environment

- Как в [EXP_001](EXP_001_BASELINE.md): GKE `us-central1`, `g2-standard-8` + 1 × L4; vLLM 0.30.0, Qwen2.5-7B-Instruct bf16, `k8s/serving/vllm.yaml` (`max-num-seqs 256`, `max-num-batched-tokens 2048`, chunked prefill, prefix caching), KV cache 53,696 tokens = 3356 блоков × 16.
- Client: `client.load` в Pod на системной ноде, хэш кода в meta (`client_code_sha256`).

Задержки в мс; серверные значения — средние за окно. `steady tok/s` — все выходные токены (любой фазы) между первой и последней отправкой measure-запроса, делённые на этот интервал (`analysis/aggregate.py: steady_output_tok_s`).

**Что показал пилот:**

- **Клиент не узкое место:** не больше 16% одного CPU при c=128.
- **Метрика `out tok/s` в коротком окне смещена.** Она считает только токены measure-запросов, а окно начинается, когда сервер ещё дорабатывает прогревочные. При stagger это занижало её на 13–19% (c=8, c=32), хотя `steady tok/s` у обоих вариантов совпадает (116 / 116, 296 / 316). Значит, «потери throughput от stagger» в пилоте — артефакт определения окна, а не свойство сервера. Для Exp1 основная метрика пропускной способности — `steady tok/s`, а окно удлинено до 120 с.
- **Синхронные волны.** При старте всех воркеров сразу TTFT p50 в 3–5 раз выше (c=8: 915 против 312 мс; c=32: 1601 против 337 мс), а TPOT ниже (61.9 против 66.8 мс). E2E при этом почти одинаковый (8781 против 8806 мс): одна и та же работа prefill либо стоит перед первым токеном у всей волны, либо вклинивается в decode уже идущих запросов. Задержка в волнах видна в `server prefill` (708 против 255 мс), а не в очереди (0 в обоих случаях).
- **c=128: упор в KV cache.** KV usage доходит до 1.00, 30–32 preemption, `running` колеблется между ~78 и ~100 (ниже `max_num_seqs` 256 и ниже 128), `waiting` держится на ~40 (`timeseries` c=128). Это согласуется с оценкой ~84 полных последовательностей. TTFT определяется очередью: серверный queue time 7–9 с. Все признаки указывают на KV как ограничивающий ресурс; `waiting_by_reason` (`capacity`) этого сам по себе не различает.
- **Пропускная способность** растёт до c=64 (~400 tok/s, ~23× от c=1) и при c=128 не растёт (~360 tok/s в обоих вариантах). Один прогон на точку, поэтому величину спада и её причину по пилоту не утверждаем.
- **Серверный `gen tok/s`** при c ≥ 64 на 10–25% выше клиентского (467 против 403 при c=64, 451 против 358 при c=128). В пилоте причина осталась невыясненной. В полном прогоне (окно 120 с, прогрев 30 с) расхождение пропало (≤ 2%), то есть оно связано с коротким окном пилота, см. Interpretation.

**Решения для полного прогона** (`configs/scenarios/exp1_concurrency.yaml`):
- `stagger_s: 20`: меряем установившийся равномерный поток, а волны остаются описанным в пилоте худшим случаем. 20 с ≈ E2E при c ≤ 64, так что старты распределены примерно по одному циклу.
- `duration_s: 120` вместо 90: при c=128 E2E ~41 с.
- Уровни 48 и 96 добавлены вокруг оценки KV ёмкости (~84).

## Hypothesis

Записана после пилота, до полного прогона:

- `steady tok/s` растёт сублинейно до c=64 (~400 tok/s), между 64 и 96 выходит на плато, при 128 не выше, чем при 64.
- Ограничивающий ресурс при c ≥ 96 — KV cache: KV usage ≈ 1, preemptions > 0, `running` ниже c и ниже `max_num_seqs`. При c ≤ 64 preemptions 0 и `waiting` ≈ 0.
- При stagger TTFT p50 до c=32 остаётся ~300–350 мс (один prefill 512 токенов, разделённый с decode), при c=64 растёт до ~1 с за счёт времени prefill, а не очереди; при c ≥ 96 TTFT определяется queue time.
- TPOT p50 монотонно растёт: ~57 (c=1) → ~67 (c=8) → ~100 (c=32) → ~135 (c=64) → ~175 мс (c=128).
- Разброс медиан между повторами по `steady tok/s` и TPOT < 5% на всех уровнях без preemption.

## Interpretation

**Кривая по фазам** (для этой конфигурации, 512 → 128):
- **c = 1…8, почти линейный рост:** каждый клиент получает 84–94% скорости одиночного потока. Шаг decode остаётся memory-bound, и дополнительные последовательности почти бесплатны: TPOT растёт с 56.6 до 66.7 мс, а throughput — в 6.7 раза.
- **c = 16…64, эффективная область с убывающей отдачей:** throughput растёт до 430 tok/s (24.7×), но TPOT увеличивается до 144 мс. Очереди нет (`waiting` 0, queue 0), KV до 71%, preemption 0.
- **c ≥ 96, насыщение по KV cache:** KV usage в среднем 0.92–0.94 и доходит до 1.00, на каждый прогон 42–78 preemption, одновременно выполняется в среднем ~86 последовательностей при c=96 и при c=128. Это совпадает с оценкой ёмкости KV в ~84 полных последовательности (53,696 / 640). Остальные запросы ждут в очереди: при c=128 серверный queue time 8.1 с из 10.9 с TTFT. Рост c от 64 до 96 даёт +9% throughput, от 96 до 128 — ещё +3%, а TTFT p50 растёт в 3 и затем ещё в 5 раз. `waiting_by_reason` показывает только `capacity`, но сочетание KV ≈ 1, preemption и `running` ниже c и ниже `max_num_seqs` (256) указывает на KV как на ограничивающий ресурс.
- **Рабочая точка.** Наибольший throughput без очереди и без preemption — c ≈ 64 (430 tok/s, TTFT p95 0.74 с, TPOT ~144 мс). Выше этой точки прирост throughput мал, а латентность растёт резко. Какая точка «правильная», зависит от SLO, а не от кривой.

**Проверка гипотезы:**

| Пункт | Итог |
|---|---|
| Throughput выходит на плато между 64 и 96, при 128 не выше, чем при 64 | **частично опровергнут**: рост резко замедляется после 64, но c=128 на 13% выше c=64 |
| При c ≥ 96 ограничивает KV, при c ≤ 64 preemption 0 и `waiting` ≈ 0 | подтверждён |

**Почему пилот ошибся на c=128.** В пилоте `steady tok/s` при c=128 был ~360 tok/s, в полном прогоне — 485. Прогрев 20 с при E2E ~41 с не выводил систему в установившийся режим: в окно замера попадал разгон, когда 128 запросов приходят разом и `waiting` подскакивает до ~110 (`timeseries` пилота). Отсюда же и расхождение серверного и клиентского throughput в пилоте: в полном прогоне его нет. При c=64 TTFT в пилоте со stagger был ~1 с против 508 мс здесь: `stagger_s=10` вместо 20 разносил старты не на весь цикл.

**Наблюдения без объяснения:**
- **Ступенька TTFT между c=1 и c=2:** 172 → 308 мс, дальше почти плоско до c=32. Серверный prefill растёт со 155 до 252 мс, очередь 0. При c ≥ 2 prefill нового запроса всегда идёт в одной итерации с decode другого. Что делает такую итерацию на ~100 мс дольше чистого prefill (путь выполнения смешанного батча, async scheduling или что-то третье), по этим метрикам не определить.
- **TPOT при c=96 выше, чем при c=128** (192 против 179 мс) при одинаковом среднем `running` (~86). Разброс между повторами меньше 1%, так что это не шум. Возможная связь с тем, как часто итерации включают prefill и recompute после preemption, не проверялась.
- **ITL max 6–11 с при c ≥ 96** при ITL p99 ~0.6 с. Это согласуется с preemption (последовательность вытесняется и потом пересчитывается), но связь по отдельным запросам не проверялась.

## Limitations

- Одна длина запроса (512 → 128) и `ignore_eos`: все запросы одинаковые. При разной длине выхода KV заполняется иначе, и граница насыщения сдвинется.
- Closed loop: при перегрузке клиенты просто ждут, так что поведение при поступлении сверх пропускной способности не видно (это open-loop эксперименты).
- Разнесённый старт (`stagger_s` 20) — равномерный поток, а не худший случай. Синхронные волны (одновременный приход) описаны только в пилоте, одним прогоном на уровень.
- GPU utilization и пропускная способность памяти не измерялись (DCGM в M3/M5): о том, где decode упирается в память или в вычисления, данные косвенные.
- Одна сессия кластера, одна нода, одна версия vLLM. Клиент `dirty` после `3aa7230`, хэш кода в meta.
- Метрика `out tok/s` (только measure-запросы) при c ≥ 96 занижена на 10–15% относительно `steady tok/s`, выводы сделаны по `steady tok/s`.

## Next question

- **Что ограничивает ёмкость KV и как её поднять:** длина контекста (Exp2), длина выхода (Exp3), `gpu-memory-utilization`, FP8 KV cache. Exp1 показывает, что граница насыщения определяется числом последовательностей, которые помещаются в KV.
- **Откуда ступенька TTFT между c=1 и c=2:** серверное время prefill растёт со 155 до 252 мс без очереди. Проверить профилированием итераций или варьируя `max-num-batched-tokens`.
