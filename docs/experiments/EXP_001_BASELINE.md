## Question

Каковы TTFT, TPOT и E2E одного запроса без конкуренции при prompt 512 / output 128, и насколько они воспроизводимы от прогона к прогону? Эта точка — отправная для Exp1 (c=1).

## Environment

- Series: `l4-qwen7b-bf16-v1`
- Meta: `results/raw/l4-qwen7b-bf16-v1/<run_id>_exp0_baseline_c1_r{1..5}.meta.json`
- Environment B: GKE `us-central1`, `g2-standard-8` + 1 × L4; vLLM 0.30.0 (`k8s/serving/vllm.yaml`), Qwen2.5-7B-Instruct bf16, KV cache 53,696 tokens
- Client: `client.load` в Pod на системной ноде через ClusterIP Service; инструмент сверен с `vllm bench serve` ([VALIDATION_VLLM_BENCH.md](VALIDATION_VLLM_BENCH.md)); commit `3aa7230` + незакоммиченные правки, хэш кода в meta (`client.git.client_code_sha256`)

## Hypothesis

Гипотеза записана до получения данных:
- **TPOT ≈ 56.6 мс**, как в EXP_000: при batch=1 decode ограничен чтением весов, и контекст 512 + 128 вместо ~300 почти не добавляет трафика KV (640 × 56 KiB ≈ 35 MB против 15 GB весов).
- **TTFT ≈ 170 мс**: серверный prefill 512 токенов ~156 мс (live smoke) плюс ~15 мс на сеть и HTTP.
- **Разброс между повторами мал**: медиана TPOT отличается меньше чем на 1%, медиана TTFT — меньше чем на 5%. Шаг decode почти детерминирован (EXP_000: ITL p99/p50 = 1.014), а очередей при c=1 нет.

## Interpretation

- **Гипотеза подтвердилась по всем трём пунктам.** TPOT 56.6 мс (как в EXP_000), TTFT p50 170 мс, разброс медиан между повторами 0.005% по TPOT и 0.6% по TTFT, то есть заметно ниже порогов 1% и 5%.
- **Разложение TTFT.** Клиентский TTFT (среднее ~172 мс) = серверный TTFT (~158 мс) + ~14 мс. Из серверных 158 мс на prefill приходится ~155.5 мс, на очередь ~0.02 мс. Оставшиеся ~14 мс — путь вне engine: HTTP, сеть внутри VPC, отправка SSE. Отдельно эти части не мерились.
- **Prefill 512 токенов ≈ 2.7 шага decode** (155.5 / 56.6). Если грубо оценить вычисления prefill как 2 × ~6.5 млрд параметров (без эмбеддингов) × 512 токенов ≈ 6.7 TFLOP, выходит ~43 TFLOP/s, около трети номинального пика bf16 у L4 (~121 TFLOP/s dense). Это косвенная оценка без учёта attention, а не измерение утилизации.
- **E2E сходится с моделью** TTFT + 127 × TPOT: 170 + 127 × 56.6 ≈ 7358 мс, p95 измерен 7373 мс.
- **Хвосты.** В r1 TTFT p99 242 мс (max 295 мс) против ~188 мс в остальных повторах. В 4 из 5 повторов есть одиночный ITL ~170 мс (≈ 3 шага decode) при p99 58 мс. Это единичные события, на медианы они не влияют. Их источник по этим данным не определить: снимки `/metrics` раз в секунду такой гранулярности не дают.
- **Практический вывод для Exp1:** точка c=1 воспроизводится с точностью лучше 1%, поэтому в Exp1 различия между уровнями больше нескольких процентов не объясняются шумом прогона. Пилот Exp1 (c=1, отдельный короткий прогон) дал те же 171.6 / 56.6 мс.

## Limitations

- Одна конфигурация (L4, Qwen2.5-7B bf16, vLLM 0.30.0, 512 → 128) и одна сессия кластера: разброс между перезапусками сервера и между нодами не оценивался.
- Prompt — случайные token id, а не текст: токенизация в TTFT не входит.
- Клиент `dirty` (незакоммиченные правки после `3aa7230`), версия кода зафиксирована хэшем `client_code_sha256` в meta.
- Первая попытка Exp0 (12:52–13:29 UTC) дала те же значения в выводе пода, но её сырые файлы потеряны при копировании из кластера (оборвался `kubectl exec`). Данные отчёта — из повторного прогона. После этого `scripts/run-bench.sh` копирует результаты с проверкой sha256 и повторами.
